# Decisiones de arquitectura — EV2 Clandestinoz

Registro de decisiones fijas del proyecto. Cada una se tomó al elaborar el plan (3 de septiembre de 2026) a partir
del estado real del código. **No se cambian sin aprobación del dueño del proyecto.** Si una decisión se revisa,
se agrega una nueva entrada con fecha y se marca la anterior como reemplazada; no se borra.

| # | Tema | Decisión | Por qué | Alternativas descartadas |
|---|------|----------|---------|--------------------------|
| D01 | API | Una sola API Express que monta routers por módulo: `/api/auth`, `/api/nightclubs`, `/api/reservations`, `/api/employees`, `/api/tips`, `/api/taxi`, `/api/valet`, `/api/pricing`, `/api/pos`. | Un solo proceso simplifica despliegue, autenticación y transacciones entre módulos (por ejemplo propina + libro contable en la misma transacción SQL). El equipo es de 1–2 personas. | Microservicios por módulo (más infraestructura que valor a esta escala); Nest.js (reescritura innecesaria). |
| D02 | Base de datos | PostgreSQL 15, un solo esquema, migraciones numeradas en `server/migrations/` aplicadas con `npm run migrate`. | Los tres SQL actuales están duplicados y solo uno se carga; un esquema único con migraciones es la única forma de evolucionar la BD con datos reales sin perderlos. | initdb de Docker (no permite evolucionar); ORM con migraciones automáticas (se prefiere SQL explícito y revisable). |
| D03 | Libro contable | Tabla `transactions` de solo inserción (trigger que bloquea UPDATE/DELETE) + `audit_log` para acciones administrativas. | Propinas, depósitos, reembolsos y retiros son dinero real; se necesita trazabilidad inmutable para conciliar con Stripe, Mercado Pago y el POS. | Guardar saldos calculados en la fila del empleado (se corrompe con facilidad). |
| D04 | Tiempo real | El servidor WebSocket no guarda estado propio. La API publica eventos en Redis pub/sub y el WS los reenvía a clientes autenticados por JWT, filtrando por club, rol y usuario. Reconexión con `lastEventId`. | El WS actual guarda 5 mesas en memoria y se pierde al reiniciar. Separar estado (Postgres) de transporte (WS) permite reiniciar o escalar el WS sin perder nada. | Socket.IO con adaptador (válido, pero `ws` ya está en uso y basta); estado en el WS (rechazado por pérdida de datos). |
| D05 | Web | HTML + Tailwind sin paso de build, con módulo común `web/js/api.js` (token, fetch, WS, idioma, moneda) y PWA instalable. | Las pantallas ya existen y funcionan visualmente; agregar un framework obligaría a reescribirlas. La PWA permite operar el club antes de que las apps nativas lleguen a las tiendas. | React/Vue (reescritura completa); apps nativas como único cliente (retrasa el lanzamiento). |
| D06 | Móvil | Proyectos reales: Xcode (SwiftUI, iOS 16+) y Android Studio (Jetpack Compose, minSdk 26). Cliente HTTP generado o escrito a partir de `server/openapi.yaml`. | El código actual es suelto y sin proyecto; el contrato OpenAPI es el acuerdo que permite trabajar móvil y backend en paralelo. | Flutter/React Native (descarta el código SwiftUI/Compose existente). |
| D07 | Pagos | Stripe con PaymentIntents (tarjeta, Apple Pay, Google Pay, USD) y Mercado Pago (México: tarjeta, OXXO, SPEI). Zelle, Cash App y depósito directo = "pago manual" que confirma un manager, con registro en `audit_log`. | Stripe `charges.create` (usado hoy) está obsoleto. Zelle y Cash App no tienen API pública para cobros. Mercado Pago cubre los medios de pago locales del club en Nogales. | Solo Stripe (cobertura limitada en MX); PayPal como principal (comisiones y experiencia en móvil peores). |
| D08 | Retiros de empleados | Primera versión: el empleado solicita, el manager aprueba, el pago se hace fuera del sistema y se registra. Payout automático a CLABE/ACH queda para una fase posterior. | Un payout automático requiere Stripe Connect o un proveedor local, contratos y verificación de identidad; no es razonable antes de operar con datos reales. | Payouts automáticos en v1 (riesgo financiero y legal alto). |
| D09 | Seguridad base | `helmet`, `express-rate-limit`, validación con `zod`, JWT de acceso 15 min + refresh token revocable en BD, CORS estricto a los dominios reales, cuentas bancarias cifradas con `pgcrypto` y enmascaradas, nunca se guarda número de tarjeta. | Requisitos mínimos para manejar datos personales y financieros de clientes y empleados. | Sesiones con cookies (dificulta apps nativas); JWT de larga duración sin revocación. |
| D10 | Flirt | Opt-in explícito para recibir, bloqueo y reporte de usuarios, límite de 20 por hora, verificación 18+ en el registro, bandera `ENABLE_FLIRT` para desactivar el módulo sin afectar el resto. | Riesgo de acoso y de menores; el módulo debe poder apagarse en caliente. | Flirt abierto sin consentimiento (rechazado). |
| D11 | Servidor | VPS Ubuntu 24.04 (4 vCPU / 8 GB) con Docker Compose; stacks separados para staging y producción; Postgres y Redis sin puertos publicados; Caddy (SSL automático) o nginx + certbot; respaldos diarios con restauración probada mensualmente; Uptime Kuma con alertas. | Costo bajo (20–30 USD/mes), control total, y el `docker-compose` existente se reutiliza. | Plataforma administrada (Railway/Render: más costo por servicio y menos control de red); servidor en el propio club (sin respaldos ni disponibilidad garantizada). |
| D12 | CI/CD | GitHub Actions: lint + tests en cada PR; en `main` se construyen imágenes, se publican en GHCR y se despliega a staging automáticamente; producción con aprobación manual. Rollback por tag. | Evita despliegues a mano y garantiza que a producción solo llega lo que pasó pruebas y aprobación. | Despliegue manual por SSH (propenso a errores). |
| D13 | POS | SoftRestaurant11 es la fuente de verdad de menú, inventario y cuentas. La app envía comandas al POS y recibe estados; nunca sustituye a la caja. Simulador `pos-mock` para desarrollo y tests. El mecanismo real se confirma en el paso 0.9 antes de programar. | El club ya opera con ese POS y los reportes fiscales salen de ahí. El código actual asume rutas que probablemente no existen. | Que la app lleve su propio inventario y ventas (duplicaría contabilidad). |
| D14 | Estructura | `server/{src/{routes,services,db,middleware},migrations,seeds,tests,openapi.yaml}`, `web/`, `mobile/ios`, `mobile/android`, `deploy/`, `docs/`, `.github/workflows/`. | Separa claramente backend, clientes, infraestructura y documentación; permite CI por carpeta. | Todo en la raíz (estado anterior, inmanejable con 130 archivos). |
| D17 | Cobro de reservaciones: por noche y por evento | La mesa se vende **por toda la noche**, no por horas. `total = precio de zona + (personas adicionales × precio del boleto de esa noche) + extras`. Cada zona incluye N boletos y admite un máximo de extras (Zona Roja: 8 personas, **sin extras**; Zona Azul: 10 personas, hasta 2 extras). El **precio del boleto cambia por evento**, y el gerente puede sobrescribir precio, boletos incluidos o extras de cualquier zona **solo para un evento**, sin alterar la lista vigente. El precio de zona y el del boleto se **congelan en la reservación** al momento de reservar. Plazo de llegada: **3 horas** desde la apertura; después la mesa se libera como `no_show` y **no hay reembolso**. | Es el modelo real del negocio, confirmado por el dueño el 2026-09-03 con la lista oficial "VIP PRECIOS" vigente desde enero de 2026 y el mapa "PICK YOUR PARTY". Cobrar por hora habría facturado mal desde la primera reservación. Congelar precios evita que un ajuste de tarifas altere ventas ya cerradas. | Precio por hora con hora extra (modelo del código heredado, no corresponde a la operación); precio único por zona sin eventos (no permite noches especiales). |
| D16 | Integración POS: agente local | Un servicio de Windows en Node (`agent/`) instalado en el servidor SQL del POS (`192.168.2.108`), con usuario SQL de solo lectura, que sincroniza catálogo/inventario/cuentas hacia la API por HTTPS. Escritura de comandas solo por el mecanismo oficial de National Soft cuando exista. | La base del club es SQL Server en LAN sin acceso desde fuera; abrir puertos o exponer la base sería inseguro. El agente no toca el POS y sobrevive a caídas de red con cola local. Ver `docs/POS_REAL.md`. | Conexión directa desde el VPS (requiere exponer SQL Server); escribir comandas en la base (invalida soporte y reportes fiscales). |
| D15 | Forma de trabajo | Paso a paso según `docs/MANUAL_IMPLEMENTACION_EV2.pdf`; aprobación del dueño antes de cada cambio; verificación obligatoria por paso; bitácora en `docs/AVANCE.md`; rama por paso y merge a `main`; commits con autor Erick Lopez y co-autor Jovanny Rodriguez. | Trazabilidad y control del dueño sobre un sistema que manejará dinero y datos personales. | — |

## Reglas absolutas

- Nunca probar contra la caja activa del club ni con dinero real antes de la Fase 7.
- Nunca versionar `.env` ni secretos; nunca exponer Postgres/Redis a Internet.
- Nada de datos simulados, contraseñas por defecto ni atajos "temporales" en código que llegue a `main`.
